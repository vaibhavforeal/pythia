# The mic button in the app shell — why it was hidden, and what it takes to show it

Voice works on the website. In the Capacitor build the button is hidden
outright, because `public/voice.js` knows something the caller doesn't: no
`android/` project is committed, so nothing declares the microphone permission,
and `getUserMedia` would fail *after* the call overlay had already opened.
Hiding it was the honest thing to do at the time. It is also why voice does not
exist on the product that most callers will actually install.

## The permission is two permissions

The obvious read — declare `RECORD_AUDIO` and the button can come back — is
wrong, and wrong in the direction that produces a silent failure.

Capacitor bridges a WebView `getUserMedia` call to an Android runtime prompt in
`BridgeWebChromeClient.onPermissionRequest`. For audio capture it does this:

```java
permissionList.add(Manifest.permission.MODIFY_AUDIO_SETTINGS);
permissionList.add(Manifest.permission.RECORD_AUDIO);
```

and the result callback treats the request as granted only if *every* entry
came back true; on any false it calls `request.deny()`.

`MODIFY_AUDIO_SETTINGS` is a normal permission, not a dangerous one. Declared,
it is granted at install with no prompt. Undeclared, the launcher simply
returns false for it. So a manifest carrying `RECORD_AUDIO` alone produces an
all-true check that can never be all-true: the caller sees the system prompt,
taps Allow, and is denied anyway — with nothing in any log saying why.

That is the same failure shape as `interrupt_response` and
`input_audio_transcription`, which were the entire diff between a session that
answered and one that connected, said "listening", and never spoke. Two fields
taken from documentation, no error anywhere. The rule that came out of it holds
here: nothing ships on the strength of a doc page.

Capacitor's own library manifest declares no permissions at all, and the
generated app manifest declares exactly one, `INTERNET`. Both audio permissions
have to come from us.

## Where the declaration lives

`mobile/android/` is generated by `npx cap add android` and git-ignored, which
is the right call — it is build output, and the README says so. But a
permission that only exists inside build output is a permission that vanishes
the next time anyone regenerates it, on a machine that isn't the one where it
was added.

`mobile/sync-web.js` already answers this exact question for the web assets: it
is a small node script that post-processes generated output, documented, run
from `npm run sync`. `mobile/patch-android.js` is the same idea for the
manifest — read it, add the two `uses-permission` entries beside the existing
`INTERNET` line, write it back, and do nothing if they are already there.

The alternative was to stop ignoring `mobile/android/` and hand-edit the
manifest once. Rejected: it inverts the project's stated posture on generated
native output and drags a large tree through review, to buy two lines that a
20-line script keeps correct forever.

Failure modes are loud on purpose. A missing manifest says to run
`npx cap add android` rather than silently doing nothing. A manifest with no
`INTERNET` anchor throws, because that means the Capacitor template changed and
guessing at an insertion point is how you get a manifest that parses and
doesn't work. The one quiet case is `android/` not existing at all, which is
legitimate — `npm run sync` runs before the native project is created.

## The button

The blanket native hide goes. The permission is then requested when the caller
taps the mic, which is the pattern Android wants anyway — at point of use, not
at launch — and it already happens before the server is contacted, so a denial
still costs no session and no metered minute.

The `NotAllowedError` message needs to change with it. "Allow the microphone
for this site — the padlock in the address bar" is sound advice in a browser
and nonsense inside an installed app, where the recovery is Settings › Apps ›
Pythia › Permissions. Same branch, different text depending on
`PythiaAuth.native`.

## Verification

`node --test` covers the patcher: both permissions land, a second run is a
no-op, a manifest already holding one gains only the other, and a manifest
without the anchor throws rather than writing something plausible.

What the tests cannot cover is whether audio actually captures on a device.
That is a physical claim, and it has now been made: on a Galaxy A52s
(SM-A528B, Android 14), the prompt appeared, Allow was tapped, and Pythia both
heard the caller and answered. Voice works in the app.

The permission dump on that device is the argument for the second permission,
stated by the platform rather than by us:

```
MODIFY_AUDIO_SETTINGS: granted=true      ← normal permission, auto-granted because declared
RECORD_AUDIO:          granted=false     ← dangerous, awaiting the runtime prompt
```

Undeclared, `MODIFY_AUDIO_SETTINGS` reads `false`, and Capacitor's all-must-be-true
check denies the call after the caller has already tapped Allow.

## What the first real build turned up

Two things stood between a correct manifest and a working app, neither of them
about the microphone.

**The app died three seconds after launch, every launch.**
`PushNotifications.register()` throws `IllegalStateException: Default
FirebaseApp is not initialized` because `app/build.gradle` applies the
google-services plugin only when `google-services.json` is present in `app/` —
and it was sitting in `mobile/`. It surfaces as a FATAL EXCEPTION on the
CapacitorPlugins thread, so no JS `try/catch` reaches it, and nothing on screen
says what happened. `patch-android.js` now copies the file for the same reason
it patches the manifest: `android/` is generated, so anything it needs must
come from a directory that is committed.

**Google sign-in cannot work in the webview.** `app.html` renders the button as
`<a href="/api/auth/google">`, and an anchor bypasses the `fetch` patch in
`api.js`, so the webview resolves it against its own bundle:

```
D/Capacitor: Handling local request: https://localhost/api/auth/google
```

Pointing the href at `PythiaAuth.apiBase` fixes the navigation and not the
problem — Google returns `disallowed_useragent` for OAuth in an embedded
webview. The real fix is a Custom Tab plus a deep-link return carrying the
bearer token, which needs the intent filter and `assetlinks.json` already
listed in the mobile README. Not done here. Until it is, the app can only be
signed into by a method that goes through `fetch`.

## Still open

- iOS. `NSMicrophoneUsageDescription` in `Info.plist` is the equivalent, and
  the same argument applies, but no `ios/` project exists and it needs macOS to
  generate. The patcher covers Android only, and says so.
- Google sign-in in the app, per above. It is the only login method prod
  accepts, so the app is unusable for real users until it lands.
- The Gradle wrapper needed a local distribution and a JDK override to build on
  this machine. Both live in git-ignored `android/`, so they are not durable;
  if the next build fails at Gradle, that is why.
